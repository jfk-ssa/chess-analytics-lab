# M7 depth — working plan (2026-10-04)

M6 is accepted for the bounded typed-tool analyst. M7 is **in progress**;
there is no new model result or expanded corpus yet. Keep the M6 v2 responses,
scorer and failures frozen. No M6 holdout case may be reused as an untouched
test case after inspection.

## Sequence and gates

1. **Clock-coverage failure analysis and development.** The two M6 v2 misses
   were answerable coverage questions that received safe `unsupported`
   responses. Strengthen the planner's instruction that a specified bucket's
   coverage is computable even when evaluations are sparse. Build new
   development paraphrases and negative controls for missing buckets, causal
   claims, private data, and full-month extrapolation. Validate each reference
   against the independent raw-PGN tally and checked tool. This is offline
   harness evidence until actual model responses are scored.
2. **Larger independent evaluation.** Create at least 50 new cases with
   family-disjoint development and test templates, including clock coverage,
   openings, cohorts, ambiguity, and high-severity boundaries. Freeze references,
   prompt/configuration, dataset ID, case hashes, and scoring rules before any
   live test. Preserve every response and failure. A later live run needs a
   separate explicit gross cap and a preflight quote; the M6 cap is closed.
3. **Data depth feasibility.** Measure what a bounded extension of the August
   source prefix would cost in bytes, time and disk and whether it would add
   observed dates or meaningful clock/evaluation coverage. Extend only with a
   fixed cap and a documented coverage benefit. Keep a partial source labeled
   partial and never interpret prefix rates as whole-month rates.
4. **Controlled engine enrichment, if justified.** Stockfish is not installed
   locally. Before adding it, define a small deterministic game/move sample,
   fixed engine version, depth/node/time budget, and comparison against existing
   provider evaluations. Proceed only if expected analytical value justifies
   runtime and artifact size. Engine results cannot repair missing-data bias in
   the original source by themselves.

M7 acceptance requires a measured benefit and resource cost for each adopted
addition, passing offline integrity/access checks, exact new reference counts,
and explicit separation of deterministic replay from actual model results.
Provider alternatives are excluded from M7 while inference costs remain at
the current cents-per-evaluation level. Airflow and Jev remain separate follow-ups;
the recommender remains backlog.

## Baseline and first change

M6 v2: 82/84 answerable, 36/36 ambiguity/unsupported, 18/18 high severity,
120/120 evidence integrity, $0.009968525 gross for 120 requests. The only two
scored failures were clock-coverage abstentions in one semantic-context repeat.
The current August 2026 source is a 40,000,000-byte compressed prefix with
100,000 complete games and observed UTC coverage of August 1 only. The
published archive metadata lists about 92 million games and 30.1 GB for the
month; a uniform per-day average would be about 3 million games and 0.97 GB
compressed. This is only a feasibility estimate, not evidence of daily
uniformity. Raising the byte cap slightly while keeping the 100,000-game cap
cannot add another day. A multi-day sequential-prefix build may be roughly
30 times the current game count, so investigate a more targeted bounded
sampling method before downloading or processing that volume. The first M7
code change adds a narrow
coverage-routing instruction to the planner. A new [12-case clock development
set](../evals/cases/m7_clock_dev.json) has eight answerable coverage paraphrases
across four buckets, one missing-bucket clarification, and three unsupported
controls. The [offline validation](../reports/M7-clock-dev-offline.json) matched
all 12 expected statuses and raw-PGN-derived counts through the checked tools.
This is an oracle/replay check, **not an observed model improvement**. No live
M7 request has been sent.
