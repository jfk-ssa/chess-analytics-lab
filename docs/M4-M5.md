## M4: dashboard and memos

Install and launch the optional local dashboard:

```sh
UV_CACHE_DIR=.uv-cache uv sync --locked --no-editable --extra dashboard --extra dbt --offline
.venv/bin/streamlit run analytics_m4/dashboard.py
```

The six views cover overview/coverage, opening comparisons, clock-pressure
analysis, data quality, offline analyst, and evaluation evidence. Every view
displays the checked analytical ID and observed dates. Opening filters expose
color, rating band and exact time control; clock rates show eligible and
evaluable denominators together. The UI uses built-in Streamlit charts and
tables, with no hosted service or custom JavaScript stack.

The [opening memo](M4-OPENINGS.md) compares Black 1400–1599 at exact 60+0.
Its descriptive adjustment applies common pooled weights to three
player-minus-opponent rating strata. Seeded focal-player cluster bootstrap
intervals reflect dependence within this observed prefix, not uncertainty
about the full month. The [clock memo](M4-CLOCK.md) reports sparse source
evaluation coverage and the exploratory >=200 cp deterioration proxy; no
independent-move interval or causal claim is attached. Regenerate figures and
both memos with `PYTHONPATH=. .venv/bin/python scripts/build_m4_report.py`.
The [figure inputs](../reports/M4-figures.json) and
[independent comparison](../reports/M4-reference-check.json) are saved.
The [six-view smoke result](../reports/M4-dashboard-smoke.json) records no

`PYTHONPATH=. .venv/bin/python scripts/check_m4_dashboard.py`.

## M5: checked tools, replay and evaluation harness

`analyst_m5` provides `list_metrics`, `get_metric_definition`,
`get_dataset_coverage`, `query_metric`, `compare_openings`,
`analyze_clock_pressure` and `compare_clock_buckets`. The default path
accepts a typed plan with at most four checked tool steps. Tool arguments
are validated and metric SQL uses a read-only DuckDB connection with
parameterized values. Answers contain status, interpretation, dataset ID,
filters, values, evidence IDs, caveats and a deterministic explanation.
Metadata and user questions are treated as data, never as instructions.

Offline commands:

```sh
.venv/bin/python -m analyst_m5 replay 'What fraction of completed eligible games drew?' --fixture evals/replay_plans/draw_fraction.json
.venv/bin/python -m analyst_m5 eval --split both
```

A typed plan can be run with `python -m analyst_m5 typed QUESTION --plan FILE`.
The dashboard's analyst view also offers typed and fixture-replay runs. The
[50-case manifest](../evals/cases/m5_manifest.json) freezes 30 development
and 20 test cases, with each required category represented in both and no
shared template family across the splits. Plans
are stored separately from reference answers. The
[50/50 saved result](../reports/M5-both-harness.json) is **fixture replay and
scorer validation**, not model accuracy. The test references have been used
for offline harness validation and must not be represented later as an
untouched model holdout if inspected during tuning. The M3 12-case draft
remains a separate historical artifact.

Free-form SQL is disabled. The typed path has no SQL/file/network/extension
tool; access-boundary tests reject such attempts. A future SQL benchmark
requires an independently isolated worker and dedicated tests before it is
enabled. The deterministic tools do not implement a semantic repair step;
invalid plans fail clearly and are not silently retried.
The 30-second tool response check runs after a read-only query returns; it is
not a hard process-kill timeout. Add a killable worker before exposing live
model-driven tool execution to untrusted requests.

## Personal live adapter remains disabled

The Responses planner is code-complete enough for a later personal experiment
but **has not made a live call or received a model response**. It accepts only
an explicitly supplied personal config file with `enabled=true`, a personal
account acknowledgement, exact model ID, positive input/output prices, a
maximum output-token count and positive `max_run_usd`. It reads only the
explicit `CHESSLAB_OPENAI_API_KEY` environment variable. A
conservative request-cost bound is checked before transport; missing usage
fails closed. Successful and failed attempts are retained under ignored
`data/analyst_attempts/` without storing the key. The checked tools, not the
provider, compute all numerical claims. No provider configuration has been
enabled or personal key supplied in this milestone. Before a live run, verify
current model availability and prices for the personal account and set a
specific spending cap. See [example config](../config/personal_provider.example.json).
The [disabled-gate check](../reports/M5-disabled-gate.json) records a rejected
CLI attempt before transport; the full failed attempt remains in ignored local
data.

The local acceptance checks are in [STATUS.md](STATUS.md). No hosted CI run,
live benchmark, cost measurement or provider entitlement is claimed.
