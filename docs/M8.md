# M8 Jev decision note — queued

M8 starts only after the core analyst has an accepted M7 quality checkpoint
and a concrete narrow decision task that Jev can evaluate. Keep the current
DuckDB pipeline and typed-tool analyst as the baseline. Jev's row judgments
and typed choices are candidates for routing, ranking, or review; they do
not replace SQL arithmetic or the narrative analyst.

Compare three integration routes on the same held-out labels, thresholds,
fallback policy and measured cost/latency:

1. **Direct Jev API behind a small typed adapter.** This is the simplest
   route for an agent-side routing or review experiment and keeps database
   extension behavior out of the first comparison.
2. **DuckDB Jev extension.** DuckDB lists a community `jev` extension with
   `jev`, probability, score, and choice functions. This is the first SQL
   route to test because the project already uses DuckDB. Confirm pinned
   DuckDB/macOS-arm64 compatibility, extension provenance, network and
   credential behavior, and whether the row-wise API offers a real benefit
   over a typed adapter before installing it.
3. **pg_jev.** The PostgreSQL extension is promising for a future Postgres
   learning slice. Its current setup calls for PostgreSQL, `plpython3u`,
   superuser installation, and a TypeSafe API key. Add a local Postgres
   comparison only if its integration or query behavior is worth operating
   a second database for this small project.

Acceptance needs offline contract/replay tests, independently labeled
held-out decisions, calibration or selective-coverage evidence where the
task supports it, actual usage-based gross cost and latency, and a fair
rule-based and current-analyst baseline. Check current API entitlement and
prices before proposing a separate live cap; recommend a concrete cap with
a conservative preflight. Do not use workplace credentials or infer API
access from a login. The personalized recommender remains outside M8.
