# M8 Jev research and routing experiment

The rank-1 routing slice has actual direct Jev and existing-analyst results.
Its [educational runbook](JEV_ROUTING_RUNBOOK.md)
explains the frozen cases, runnable comparison, direct API adapters, score
interpretation, spend preflights, and the DuckDB packaging limit. The later
[paired final-answer lab](JEV_END_TO_END.md) found no quality, cost or latency
benefit from a narrow Jev boundary gate on 32 new cases, so the existing
analyst remains the product baseline. This page retains the broader
opportunity ranking; both measured studies are separate from production.

M7 is accepted. M8 is a separate, bounded classification experiment, not a
replacement for checked metric tools, SQL arithmetic, or the Sol narrative
analyst. The current product has six allowlisted metric definitions and three
answer states (`answered`, `needs_clarification`, `unsupported`). Its December
holdout has 41 answerable, four clarification and five unsupported cases. A
new Jev component has to improve a measured decision on fresh labels, not
merely reproduce the accepted 150/150 fixed-case Sol result.

The accepted M7 code and evidence are pinned by the local Git tag
`m7-baseline` at `f814377`. Keep one repository and one checked-tool core.
Implement each Jev idea behind an explicit experiment mode (`baseline`,
`jev_intent`, `jev_review`, `jev_evidence`, `jev_cost`); run one intervention at
a time against identical frozen inputs and log mode, code revision, model,
thresholds and outputs. Short-lived branches may be used for development,
but comparison results must be produced from pinned versions and evaluated
by the same scorer. The baseline path remains runnable without TypeSafe
credentials. Only compare combined Jev modes after individual effects are
known.

## Ranked decision opportunities

| Rank | Classification step | Why here | Baseline and decisive measure |
|---|---|---|---|
| 1 | **Question intent plus boundary routing.** A Choice selects a closed metric/handler ID or `clarify`, `unsupported`, or `fallback` from a compact question, metric catalog and observed-coverage summary. Code validates filters and actual coverage. | Direct fit to the typed analyst; prevents a wrong tool route or an answer to a request the data cannot support. Independent labels are feasible from the existing request taxonomy. | Keyword/rule router and structured-output LLM on the same new family/date split. Measure handler accuracy, unsupported recall, unnecessary clarification, end-to-end answer quality, fallback rate, latency and total gross cost. |
| 2 | **Analytical wording review.** Separate narrow Noul judgments flag a causal assertion, a claim that sparse source evaluations represent all moves, or a conclusion that exceeds its evidence. Code still checks exact values/evidence IDs. | A useful second boundary after tools run, especially for clock-pressure interpretation. Review can be advisory until false rejections are measured. | Existing exact validators and human-reviewed claim labels. Measure harmful-claim detection, false rejection of correct answers and downstream correction rate. Never use Jev as its own sole grader. |
| 3 | **Candidate evidence/metric relevance.** Classify a short, rule-generated list of candidate metric definitions or evidence packets for the question, then feed only approved IDs to the planner. | Could reduce irrelevant context or a wrong metric family as the catalog grows; benefit is modest with today's six metrics. | Keyword or deterministic shortlist. Measure top-k relevance, downstream answer quality, latency and total cost. Do not let Jev invent an ID or SQL. |
| 4 | **Cost-aware execution routing.** Choose template, economical model or stronger model from a closed set after deterministic eligibility checks. | Potential future saving, but the December Sol holdout cost $0.1778959 for 150 completed calls, about $0.00119 per call. A classifier's latency and mistakes matter more than tiny savings now. | Always use the economical model and a simple rule. Compare gross cost per correct answer at matched answer coverage and boundary quality, including Jev calls and fallbacks. |

Do not spend Jev calls to calculate win rates, compare dates, infer missing
clocks, reclassify provider opening tags at scale, or decide whether a move
crosses a numerical centipawn threshold. Those are deterministic code or
versioned lookup tasks. Raw game rows have no sufficiently valuable free-text
classification target yet. A SQL-extension demonstration should therefore
classify a bounded table of independently labeled **analyst questions** on
the same rank-1 task, with only question and compact coverage fields sent.

## Integration routes for the rank-1 experiment

1. **Direct TypeSafe API with a typed adapter:** first product route. Pin
   `jev-1.13.0`, freeze the Choice schema/options and capture resolved model,
   full probabilities, usage, failures and fallback reason. One compact state
   can carry more than one independent narrow question. No new database is
   required.
2. **DuckDB community `jev` extension:** first database route, in an isolated
   environment over the same question rows and labels. It exposes
   `jev_choice`, `jev_eval`, `jev_prob` and `jev_stats`, and has row/character
   statement limits. The repository currently pins DuckDB **1.4.1** on
   macOS arm64; published extension availability and binary compatibility
   for that exact build failed with HTTP 404. Do not change the core lock or load
   a networked extension into the production read-only analyst connection to
   make the comparison work. Row contents leave for the TypeSafe API.
3. **pg_jev:** optional local PostgreSQL learning slice over the identical
   question rows, if the direct/DuckDB comparison shows useful behavior.
   It requires a PostgreSQL server, `plpython3u` and superuser installation;
   this repository has no PostgreSQL client/server in its local tool path.
   It is not justified as core infrastructure for six DuckDB metrics.

TypeSafe documents Choice, Score and Noul as typed decisions, and publishes
`jev-1.13.0` at **$0.042 per million input tokens**, with no output-token
charge. The current 40-question [offline preflight](../reports/M8-routing-preflight.json)
reserves **$0.010722096** for one direct Jev pass. The owner approved a
**$0.05 cumulative gross TypeSafe cap** for up to two direct passes; actual
accounted gross was **$0.002000376**. An authenticated model-list request
succeeded, and the pinned version worked in both calls, although the model
list enumerated only `jev-latest` and `jev-preview` aliases. Account balance
was not read.
The current experiment uses a frozen 80-question corpus and separate
40-question test split. The offline rules baseline scored 35/40; actual
Jev passes scored 39/40 and 37/40, and the existing analyst scored 33/40.
These are semantic-route scores. A community-extension install was attempted on pinned
DuckDB 1.4.1/macOS arm64 and returned HTTP 404, so the SQL learning slice
is currently an offline DuckDB table plus a bounded Jev SQL preview. See
the [actual-run checkpoint](../reports/M8-routing-checkpoint.json).

For account setup, the user should create a key for their **personal**
TypeSafe account from the console dashboard and place it only in the ignored
local `work/.env.typesafe` file as `TYPESAFE_API_KEY=...`. Never paste the key
into chat, source, a report or a GitHub secret for local runs. A login by
itself does not prove API access; the authenticated model-list request and
actual runs verified this account's access. The adapter reads only this
explicitly named file. Future inference needs a fresh explicit cap; the
completed M8 authorization does not cover new experiments.

## Evidence needed before integration

The current slice has 80 new manually labeled questions across the approved
metric families, ambiguity, out-of-scope inference and missing-data cases,
balanced 40/40 across development and test. Independently adjudicated labels,
additional date/family splits, and a larger sample remain future quality
gates. Compare rules, the existing structured-output LLM and Jev on
identical questions. Use full option probabilities to measure
selective coverage, critical-class recall, Brier score/reliability where
sample size permits, and repeat identical inputs plus paraphrase/option-order
perturbations. The TypeSafe `confidence` field summarizes distribution shape;
it is not empirical correctness probability. Document numerical, literal
reading, long-state and option-order failures, and do not infer bit-for-bit
repeatability. Then compare the full analyst with and without the selected
router under a predeclared quality-regression allowance. Preserve all raw
attempts and distinguish offline replay from actual model results.
